# visual-consensus

論点が多いときは、チャットの長文の代わりに「答えられる資料」を渡す。
利用者はブラウザで資料を開き、判断を選び、行や画面案にコメントし、画像の一点にピンを打つ。
回答は資料の横のフォルダに `answers.md` として保存され、エージェントはそれを読んで次の回の資料を作る。

このスキルが使う道具は Node.js 22.15 以降の `engine/build.mjs` だけで、外部パッケージは要らない。
以下の `<skill>` はこの SKILL.md があるフォルダを指す。

## 使う場面

- 決めてもらう判断が3つ以上ある。または、理由や比較を見せてから選んでほしい。
- 画面案、スクリーンショット、図に対して、場所を指した指摘をもらいたい。
- 一度で決まらず、回答を受けて資料を直す往復が見込まれる。

1〜2問ならチャットで聞く。読ませるだけの説明資料には使わない。

## どちらの場面か

- **新しく確認したい** → 「A. 資料を作って渡す」
- **利用者が「回答した」と言った** → 「B. 回答を読んで次の回を作る」

## A. 資料を作って渡す

```
- [ ] 1. 置き場所を決め、ひな形を作る
- [ ] 2. 論点を整理し、原稿を書く
- [ ] 3. ビルドし、エラーと警告が消えるまで直す
- [ ] 4. HTML のパスと答え方だけを伝える
```

### 1. 置き場所とひな形

利用者やプロジェクトの決まりがなければ、`docs/visual-consensus/YYYY-MM-DD-<話題>/` に置く。

```sh
node <skill>/engine/build.mjs --init docs/visual-consensus/2026-11-22-settings-screen --with-images
```

画像を使わないなら `--with-images` を外す。ひな形の原稿を書き換えて使う。

### 2. 原稿を書く

項目と部品は [原稿の書き方](references/authoring.md) を読んで使う。書く前に、論点を次の3つに分ける。

- 決めてもらうこと → 判断にする。選択肢を2つ以上用意し、推奨とその理由を示す。複数選べる問いには推奨の組み合わせを、同じ問いで複数の項目を判定する表には各項目の推奨を付ける。
- 見てもらうこと（現状、案、比較） → セクションの中の行にする。画像は指摘してほしい場所が読める大きさで載せる。
- 前提として伝えること → セクションの `lead` に短く書く。

文章だけでは伝わりにくいところには、画像や図を付ける。目安はその行を単体で理解するのに頭に置いておく前提の数で、3〜4個を超えるなら文章だけにしない。順番・多くの観点での比較・条件の組み合わせは図や表に、画面や物の見た目にかかわる話は、文章で言い切れても画像（スクリーンショットなど）にする。それ以外は文章で書く。使い分けは手引きの「図表で理解を助ける」に従う。

資料の出来は、利用者が迷わず短時間で答え終えられるかで決まる。次の形は答えにくい。

- 推奨に理由がない。または、どの選択肢にも長所しか書いていない。
- 選択肢で聞ける問いを、自由記述にしている。
- 1つの判断に、別々に決めるべき2つの問いが入っている。
- 画像を載せているが、どこを見ればよいか本文で示していない。
- 同じ論点を、複数のセクションで重ねて聞いている。
- 順番や組み合わせが要の話を文章だけで説明している。逆に、2〜3文で済む話に図表を付けている。
- 見た目にかかわる話（画面の状態、案、不具合など）を、画像なしに文章だけで説明している。
- 判断の番号が画面の並び順とずれている（最初のセクションが D2 など）。「D6w」のような枝番を使っている。
- 本文に書いた件数（「8つの論点」など）と、実際の判断の数が合わない。
- 推奨の理由に、判断が変わる条件（数値、前提、まだ確かめていないこと）がない。読み手は推奨をどこまで信じてよいか分からない。

### 3. ビルドと修正

```sh
node <skill>/engine/build.mjs docs/visual-consensus/<フォルダ>/content.mjs
```

成功すると `out/<題名>.html　3セクション・9行・判断4件・指摘0件` のような1行が出る。
原稿に誤りがあると、直す場所と候補を示して止まる（例：「判断 D3 の recommended『月曜』が options にありません」）。示されたとおりに直して、成功するまでビルドし直す。

### 4. 利用者に伝える

伝えるのは次の3点だけにする。

- HTML のパス。Edge か Chrome で開いてもらう（ほかのブラウザでは保存できない）。
- 答え方：上部の「保存先を選ぶ」で `out/answers` フォルダを選ぶと、回答が自動で保存される。
- 答え終わったら、チャットで知らせてもらう。

資料の質問をチャットに並べ直さない。両方にあると、利用者はどちらに答えればよいか迷う。

## B. 回答を読んで次の回を作る

回答への返事、確かめたいこと、作業の報告は、すべて次の回の資料に書く。チャットと資料に分けて書くと、利用者はどこを読めば返事がそろうのか分からなくなる。

```
- [ ] 1. out/answers/answers.md を読む
- [ ] 2. ピンや範囲の行だけ、印付き画像を開く
- [ ] 3. 回答に沿って、該当する原稿だけを直す
- [ ] 4. 未確認の部分を、次の回で改めて聞く
- [ ] 5. ビルドし、チャットには次の回ができたことと件数だけを伝える
```

### 1〜2. 回答を読む

`answers.md` はセクションごとにまとまり、見出しにセクションの状態が付いている。
資料全体への記入は「全体へのコメント」に並ぶ。

| 見出しの状態 | 書かれていない行の扱い |
| --- | --- |
| 判断済み（コメントのない行は了承） | その案で進めてよい |
| 保留あり（D4 などの番号） | 括弧内の判断は保留中。書かれていない行も未確認 |
| 了承 | セクション全体をその案で進めてよい |
| 未確認の判断あり／記入あり（コメントのない行は未確認） | まだ確かめられていない |
| 末尾の「手を付けていないセクション」 | セクション全体がまだ確かめられていない |

判断の「保留」と「未回答」は決まっていない。
ピンや範囲の行には `images/marks/<ID>.png` が書かれている。番号の付いた印がその画像に描かれているので、場所を知る必要がある行だけ開く。

### 3〜4. 次の回の原稿

回答が指すセクションの原稿だけを直す。

- 答えが確定した判断には `settled: true` を付ける。本文を引き続き確認してほしいときは、判断だけを「決定事項」に移す。ページに判断が残っていなければ、利用者は「このセクションはOK」で本文を了承できる。セクション全体の確認が済んだらセクションにも `settled: true` を付ける。チャットなど資料の外で決めた答えは、その判断の `decided` に書く（書き方は手引き）。
- コメントに返事をするときは、`answers.md` の行頭の ID を使って原稿の `replies` に書き、何を変えたかを伝える。利用者は冒頭の「この回の返事」で左の矢印を押すと、対応する返事へ移動できる。了承した回より後に、そのセクションの未完了の項目へ返事や対応が付くと、了承のチェックが外れる。
- コメントや利用者が追加したセクションへの対応が済んだら、原稿の一番外側に `resolved: ['S-01', 'D9', 'rows:xxx']` のように書く。キーは `replies` と同じ行頭の ID を使い、返事には何を変えたかを書く。同じキーを次の回にも残すと、対応した回の番号を引き継ぐ。
- 利用者が「完了」を押した項目は、`answers.md` の末尾の「決定事項」→「完了したもの」に載る。次の回でその件を問い直さない。
- 未確認・保留・未回答の部分を、決まったものとして案に組み込まない。同じ判断を残すか、問い直す判断を立てる。
- セクション・行・判断・図の `id` は変えない。回答は `id` で原稿と結び付いているので、変えると保存済みの回答が宙に浮く。新しく足すものには新しい `id` を付ける。

### 5. ビルドと報告

A-3 と同じコマンドでビルドすると、利用者がその回に答える前の手直しは同じ回に収まり、回答が保存されたあとに原稿を変えると次の回になる。回の番号はビルドに任せ、手で書き換えない。
「保存済みの回答がある行 … が原稿にありません」と警告が出たら、`id` を変えていないか確かめて戻す。

冒頭のセクションに、次の2つを書く。

- 第N回で変えたこと。
- 確かめたこと：実行・観察して確かめたこと、まだ確かめていないこととその理由、うまくいかなかったこと。

チャットには HTML のパスと、次の回ができたこと、返事と新しい判断の件数だけを書く。例：「第3回の資料を作りました。返事が2件、新しい判断が1件あります。」保存先をつないだ資料は、回答の保存が終わると自動で新しい回を開く。資料の画面で書きかけているときは上部に「更新」が出る。ボタンにカーソルを乗せると対象が分かり、押すと入力を引き継いで新しい回を開ける。
回の合間に聞きたいことが出ても、チャットでは聞かない。その問いだけを載せた回を作る。
利用者がチャットで話しかけたときは、チャットで答える。そこで決まったことは、次の回で `decided` に残す。

## 読まないもの

次は開かない。トークンを多く使ううえ、作業に必要な情報は入っていない。

- ビルドした HTML（`out/*.html`）。画像とプログラムを中に含み、数 MB になる。
- `<skill>/engine/` のプログラム。書き方は手引きとひな形で足りる。
- `answers.json`。印の座標などの細部が必要なときだけ読む。

見た目の確認にスクリーンショットを撮るのは、画面案の表示崩れを疑うときだけにする。
