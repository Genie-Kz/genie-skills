## 原稿の形

原稿は `content.mjs` で、`export default` に資料のオブジェクトを書く。部品は `visual-consensus` から読み込む（キットの場所を書く必要はない）。

```js
import { block, fig, mock, pair, col } from 'visual-consensus';

export default {
  id: 'kakeibo-settings',          // 資料の id。回答との照合に使う
  title: '設定画面の作り直し',       // 画面の題名。HTML のファイル名にもなる
  version: 'r1',                   // 回答との照合に使う。回を重ねても変えない
  sections: [ /* セクション */ ],
  decisions: [ /* 判断 */ ],
  figures: { /* 図の台帳。画像がなければ省く */ },
  issues: [ /* 利用者から届いた指摘。なければ省く */ ],
};
```

`version` を変えると、保存済みの回答を読み込めなくなる。資料の回（第N回）と `version` は別のものである。利用者がその回に答える前に原稿を直すと同じ回に収まり、回答が保存されたあとに原稿を変えると次の回になる。回の番号はビルドが付けるので、手で書き換えない。保存先をつないで資料を開いている利用者には、新しい内容が自動で表示される。資料の画面で書きかけているときは、帯の「更新」から新しい回で続きを書ける。

## セクションと行

セクションは論点ひとつ分で、左の一覧に1件ずつ並ぶ。

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| `id` | ○ | セクションの id |
| `title` | ○ | セクションの題名。何を確かめるセクションかが分かる文にする（例：「削除の操作を誤って押せないようにする」） |
| `group` |  | 一覧で題名の上に出る短い分類（例：「通知」） |
| `lead` |  | 前提や背景を1〜2文で |
| `rows` | ○ | 行の配列 |

行は利用者がコメントできる単位で、`block(id, title, html)` で作る。`title` は回答の文脈（「行『変更案』」）にも使われるので、行の中身を表す名前にする。

```js
block('reminder-plan', '変更案', mock('reminder-m1', 'リマインダー（案）', '<p>…</p>'))
```

本文に `D1` のように実在する判断の番号を書くと、リンクになる。利用者はマウスを乗せるかフォーカスを当てると問い・推奨・今の答え・選択肢を確かめられ、押すとその問いへ移れる。

特別な行が2つある。

- `{id, title, type: 'issues'}`：利用者から届いた指摘（`issues`）を画像付きで一覧にする。最初のセクションに1回だけ置く。
- `{id, title, type: 'decisions'}`：資料全体の判断を表にし、「残りを推奨で埋める」ボタンを付ける。判断が多い資料で、最後のまとめのセクションに1回だけ置く。

セクションごとの判断は、この行がなくてもセクションの最後に自動で並ぶ。各セクションに `type: 'decisions'` を置くと、同じ一覧がセクションの数だけ重複する。

## 判断

```js
{id: 'D1', section: 'reminders', question: '「記録がない日だけ通知」をどう見せますか？',
  options: ['子項目にする', '頻度を選ぶ1つの項目にまとめる'],
  recommended: '頻度を選ぶ1つの項目にまとめる',
  context: '「毎日／記録がない日だけ／オフ」の3択にすると、説明文がなくても関係が分かります。'}
```

- `section` は、その判断を置くセクションの id。
- 判断の `id` は、最初の回では画面に並ぶ順に `D1`、`D2`…と振る。次の回で足す判断には続きの番号を付け、既存の番号は振り直さない。`D6w` のような枝番は使わない（読み上げで聞き取れず、どの判断か分かりにくい）。
- `options` には異なる選択肢を2つ以上書く。文字列か `{label: '項目ごとに合わせる', note: '別々の項目の変更を残せます。同じ項目は後から届いた値を使います。'}` を使える。`note` には選んだ結果と、何を失うかを1行で書く。
- 1つ選ぶ判断の `recommended` には推奨する選択肢のラベルを書く。3択以下で各ラベルが10文字以内、説明がない場合は横並びになる。収まらない幅や説明付きの選択肢では縦に並ぶ。
- 「その他」と「保留」はキットが足す。**はい／いいえ・する／しないの判断では `other: false` で「その他」を外す。** 表では各行に「保留」が付き、「その他」は付かない。
- `context` に推奨の理由を書く。理由がないと、利用者は推奨を信じてよいか判断できない。推奨が変わる条件（「停止を2時間取れなければ別の案」のような数値や前提、まだ確かめていないこと）と、他の選択肢を選ぶと何を失うかも書く。
- 本文で判断の数に触れるときは、実際の判断の数と合わせる。
- 選択肢は選んだあとの姿が分かる文にする（「A案」ではなく「頻度を選ぶ1つの項目にまとめる」）。

複数の項目を一緒に選べる問いには `multiple: true` と推奨の配列を指定する。`max` で上限を設け、`none` には「ほかは選ばない」という回答のラベルを書く。どちらも必要な問いだけに付ける。

```js
{id: 'D3', section: 'sync', question: '同期の対象にするものは？',
  options: ['記録', 'カテゴリの一覧', '月の予算', '表示設定'],
  multiple: true, recommended: ['記録', 'カテゴリの一覧', '月の予算'],
  max: 3, none: 'どれも同期しない'}
```

同じ選択肢で複数の指摘を判定するときは、項目の `id`、表示する `label`、その項目の `recommended` を `items` に並べる。次の回でも同じ項目の `id` を使うと回答を引き継げる。
見た目にかかわる項目には `figure` に `figures` のキーを書く。画像のすぐ下で選択でき、画像を押すと拡大して印を付けられる。`note` には、その項目で見てほしい点を1行で書く。

```js
{id: 'D5', section: 'triage', question: '指摘の振り分け',
  options: ['直す', '直さない', '後で'],
  items: [
    {id: 'I-01', label: '通知設定の説明文', figure: 'notify', note: 'どのスイッチの説明か分からない', recommended: '直す'},
    {id: 'I-02', label: '削除ボタンの位置', recommended: '後で'},
  ]}
```

## 部品

`block` は行を返す。それ以外は HTML の文字列を返し、組み合わせて行に入れる。

| 部品 | 用途 |
| --- | --- |
| `block(id, title, html)` | 行を1つ作る |
| `fig(key, caption, size = '')` | `figures[key]` の図を説明付きで出す。利用者は拡大してピンや範囲を付けられる。`caption` で、どこを見てほしいかを書く |
| `mock(id, title, contents)` | 画面案。行とは別にコメントを受け取れる。`contents` は HTML |
| `pair(one, two)` | 2つを横に並べて比べる（現状と案など） |
| `col(title, body)` | 見出しと本文の列。`pair` の中で使う |
| `note(title, body)` | 見出し付きの補足 |
| `pathflow(...steps)` | 手順を番号付きで並べる |
| `table(headers, lines)` | 表。各行の先頭のセルは行見出しになる。セルには HTML を書ける |
| `escapeHtml(value)` | 外から受け取った文字列を HTML に入れる前に使う |

画面案は配置や文言を決めるための簡単な HTML で足りる。見た目そのものを決めたい場合だけ、資料固有の CSS を `style: 'mock.css'`（原稿からの相対パス）で足す。作り込むほど原稿が長くなる。

## 図と指摘

```js
figures: {
  notify: {title: '通知タブ（現在）', file: 'fig/settings-2.png'},
},
issues: [{
  id: 'I-01', sections: ['reminders'], summary: '説明文がどのスイッチの説明か分からない',
  file: 'fig/report-1.png', preview: [182, 48, 78, 52],
}],
```

- `file` は原稿からの相対パス。ビルドすると画像は HTML に入る。
- `issues` は、利用者や第三者から届いた指摘を画像付きで見せるときに使う。`preview` は一覧で拡大する範囲で、原画像のピクセルで `[左, 上, 幅, 高さ]` を指定する。
- 図と指摘で、同じ id を使わない。

## 図表で理解を助ける

利用者がコメントで聞き返さなくても分かるように、文章だけでは追いにくいところに画像や図表を付ける。

文章だけで足りるかは、その行を単体で読んで理解するのに、頭に置いておく前提がいくつ要るかで決める。

- 人が読みながら覚えておけるのは、3〜4個までと考える（ワーキングメモリの目安）。それを超える前提を文章で順に渡すと、読み手は後ろを読むうちに前を忘れ、読み返すことになる。
- 前提が多いときは、図表や画像で前提を目の前に並べ、覚えておかなくても見比べられるようにする。たとえば、選択肢ごとの観点、出来事の順番、条件の組み合わせ、画面の部品の位置関係。
- 前提がほかのセクションにあり、前に読んだことを覚えていないと分からない行も同じ。その前提を行の中に短く書き直すか、図表に入れて、その行だけで読めるようにする。
- 見た目にかかわる話は、前提が少なくても画像を付ける。見た目は、文章にすると読み手が頭の中で組み立て直すことになり、それ自体が多くの前提になる。項目を一覧にして判断してもらうとき（まとめて判定など）も、見た目にかかわる項目には1つずつ画像を付ける。

| 内容 | 使うもの |
| --- | --- |
| 出来事の順番や、複数の相手とのやりとりが要になる | 時系列の図（SVG） |
| 3つ以上の選択肢を、2つ以上の観点で比べる | 比較表（行が選択肢、列が観点） |
| 2つの条件の組み合わせで結果が変わる | 組み合わせ表（行と列に条件、マスに結果） |
| 今ある画面や物の見た目・状態を伝える（現状、案の比較、指摘や不具合など） | 画像（スクリーンショットや写真を `fig` で）。どこを見ればよいかを本文か説明に書く |
| 画面の見た目や配置を決める | `mock` |
| 作業の手順 | `pathflow` |

次の場合は文章だけにする。図表を足しても、読む量が増えるだけになる。

- 2〜3文で言い切れる。
- 選択肢が2つで、違いが1点だけ。
- 前提や事実を並べるだけ。

図表の書き方は次のとおり。

- 図表の前に、要点を1〜2文で書く。図表を見なくても話の筋が分かるようにする。
- 具体例を1つ決め、資料全体で使い回す（例：「ランチ 1,200円」の記録を両方の端末で直す）。比較表に「例の結果」の列を入れると、選択肢の違いが具体的に見える。
- まだ決まっていないところや、選ぶと失うものには `<span class="hit">…</span>` で注意の色を付ける。目を留めてほしい数か所だけに使う。
- 行の本文の幅は約 510px しかない（右にコメント欄があるため）。表は4列まで、セルは短い句にする。
- SVG は `viewBox` の幅を 520 前後で描き、`<div class="scroll-x">…</div>` で囲む。狭い画面では縮まずに横へずらして読める。文字は 12px 以上にする。
- SVG の色は資料固有の CSS（`style`）でクラスに当て、キットの変数 `--ink`・`--muted`・`--line`・`--ui`・`--warn`・`--warn-tint` を使う。背景は暗い色なので、色を直接書くと読めなくなることがある。
- SVG は1枚で数千字になり、原稿を読み書きするたびにトークンを使う。図は1つの資料で本当に要る1〜2枚に絞る。

## 回答を受けて次の回を書く

答えが確定した判断に `settled: true` を付ける。利用者は資料の最後の「決定事項」で問いと答えを読み、補足を書ける。セクションの本文を残してすべての判断を移すと、そのページを「このセクションはOK」で了承できる。本文を含めて確認が済んだら、セクションにも `settled: true` を付ける。

資料の外で決めた答えはその判断の `decided` に書く。次は会議で決まった公開日の例。

```js
{ id: 'D3', section: 'release', question: '何曜日に公開しますか？',
  options: ['火曜', '木曜'], recommended: '火曜', settled: true,
  decided: {answer: '木曜', via: '会議'} }
```

「決定事項」と `answers.md` に「→ 木曜（会議で決定）」と出る。`via` を省くと「チャットで決定」になる。`decided` を書くときは、その判断かセクションに `settled: true` が要る。資料の中でも答えがある判断では資料の答えが載り、ビルドが警告する。

返事は原稿の一番外側の `replies` に書く。`answers.md` で返事をしたい行の先頭からキーをコピーする。図の印は図の ID と「ピン1」「範囲2」の間の全角空白も含める。

```js
replies: {
  'triage-m1': '表の幅を詰め、選択肢を項目名のすぐ右に移しました。',
  'settings　ピン1': 'この位置に保存ボタンを移しました。',
  'R-02': '確定した問いを「決定事項」に移しました。',
},
```

対応を終えたコメントや追加セクションは、原稿の一番外側で `resolved` に挙げる。たとえば次の原稿を第3回で出すと、それぞれの場所に「✓ 対応済み（第3回）」と返事が1行で表示される。行を開くと元の内容を読める。

```js
resolved: ['S-01', 'D9', 'rows:xxx', 'settings　ピン1'],
replies: {
  'S-01': '出張時の手順を本文に加えました。',
  D9: '選んでいただいた通知時刻を反映しました。',
  'rows:xxx': '予定表に担当者を追記しました。',
  'settings　ピン1': 'この位置に保存ボタンを移しました。',
},
```

キーは `answers.md` の行頭から写す。同名の行とセクションを区別する `rows:` や、印の前の全角空白も含める。対応済みを表示し続ける間は次の回にも同じキーを残す。返事の文を直しても、対応した回はそのまま表示される。

了承したセクションで、未完了の項目に次の回の返事や対応が付くと、了承のチェックが外れる。利用者は冒頭の「この回の返事」で左の矢印から返事へ移動し、確認したら「このセクションはOK」を押して再び了承できる。新しい返事や対応がないセクションは前回の了承を引き継ぐ。

利用者が「完了」を押した項目は、「決定事項」の「完了したもの」に移る。元の記入と返事を読め、「戻す」で元の欄に戻せる。`answers.md` では行末に「完了」が付く。次の回で問い直さない。

全体へのコメントに返事を付けるときは、行頭の `全体` を使う。表の項目（`items`）への返事は、`- D5　I-01　推奨どおり「直す」` の先頭から `D5　I-01` を全角空白ごと `replies` のキーに写す。

冒頭のセクションの「第N回で変えたこと」に主な変更と次に答えてほしい問いを書く。個別の変更は元のコメントへの返事で伝える。返事は冒頭の「この回の返事」にも一覧で出るので、変えたことに書き写さない。利用者は返事の下の「続けてコメント」から追記できる。`out/.edition.json` を原稿と一緒に Git に残すと、別の環境でも資料の回の番号と、各返事を書いた回を引き継げる。

## id の決まり

- 英字で始め、英数字・`-`・`_` を使う。
- 行の id と画面案の id はそれぞれ資料全体で重ねない。
- `general`、`S-数字`、`U-数字` は利用者のセクションと画像に予約されている。
- 一度出した id は次の回でも同じ対象に使う。別の対象に使い回さない。消した対象の id を新しい対象に付けると、古い回答が新しい対象に付いてしまう。

## 章をファイルに分ける

セクションが多いときは、セクションごとに別のファイルにして `content.mjs` から読み込む。直すときに該当するセクションのファイルだけを読めば済む。

```js
// reminders.mjs
import { block, fig } from 'visual-consensus';
export const reminders = { id: 'reminders', title: '…', rows: [ /* … */ ] };

// content.mjs
import { reminders } from './reminders.mjs';
export default { /* … */ sections: [reminders /* , … */] };
```

## 論点の組み立て方

- 1セクションに1論点：セクションの題名だけを読めば、そのセクションで何を確かめるかが分かるようにする。
- 先に決まるべきことを前に置く：他の判断の前提になる問い（対象の範囲、既存の利用者にも適用するか、など）は、最初のセクションに置く。
- 判断どうしのつながりを書く：ある判断の推奨が別の判断の答え次第で変わるなら、その条件を `context` に書く（例：「D2 で停止時間を2時間取れるなら、この推奨は変わります」）。
- 事実を教えてもらう問いは行にする：データ量や使っている機能など、選択肢にできない事実が要るときは、何を書いてほしいかを本文に書いた行を置き、コメントで答えてもらう。
- 分からないことを書く：資料を作る時点で確かめられなかった前提（コードを見ていない、数値が推測、など）は、該当するセクションの `lead` か `note` に書く。利用者がそこで訂正できる。
- 気付いたことも載せる：依頼にない問題に気付いたら、セクションとして足し、判断にするか、行として見せてコメントをもらう。
- 画像は根拠として使う：現状のスクリーンショットを `fig` で載せ、`caption` でどこを見てほしいかを書く。案は `mock` で隣に並べる（`pair`）。
